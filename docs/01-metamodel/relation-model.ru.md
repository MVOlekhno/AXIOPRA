# Модель связей

Связь — это направленное типизированное утверждение от одного артефакта к другому. Markdown-ссылка облегчает навигацию, но сама по себе не является смысловой связью.

## Канонические типы связей v0.1

- `depends_on` — исходный артефакт нельзя правильно понять или завершить без целевого.
- `derives_from` — исходный артефакт обоснован или рассчитан на основе целевого.
- `refines` — исходный артефакт делает целевой точнее, не меняя его замысла.
- `constrains` — исходный артефакт ограничивает допустимые толкования или реализации целевого.
- `realizes` — исходный артефакт реализует или делает целевой операционным.
- `verifies` — исходный артефакт проверяет заявленное свойство целевого.
- `tests` — исходный артефакт эмпирически испытывает целевой.
- `proves` — исходный артефакт формально устанавливает утверждение целевого в рамках заявленных предположений.
- `informs` — исходный артефакт даёт полезный контекст, но не является обязательной зависимостью.
- `produces` — завершение исходного артефакта создаёт или делает возможным целевой.
- `supersedes` — исходный артефакт заменяет целевой и обязан описывать совместимость или миграцию.
- `conflicts_with` — исходный артефакт сознательно противоречит целевому и блокирует их совместную активацию до разрешения конфликта.

## Правило направления

Метаданные читаются так: **этот артефакт RELATION целевой артефакт**. Например, тестовый артефакт с `tests: [AXP-REQ-017]` утверждает, что тест проверяет требование `AXP-REQ-017`.

## Инварианты графа

1. Каждый внутренний целевой ID разрешается ровно в один артефакт.
2. Активный артефакт не может иметь `conflicts_with` с другим активным артефактом без открытой записи о разрешении.
3. Связи `depends_on`, `derives_from`, `refines`, `realizes`, `verifies`, `tests` и `proves` не допускают петлю на самих себя.
4. Циклы зависимостей запрещены, если RFC не определяет законную сильносвязную модель и явное правило верификатора.
5. `supersedes` ациклична и направлена от нового артефакта к старому.
6. `proves` обязана указывать предположения и границу доказываемого утверждения в артефакте доказательства.
7. `tests` и `verifies` не означают `proves`.
8. `informs` не удовлетворяет обязательной зависимости.
9. Удаление артефакта блокируется, пока существуют активные входящие обязательные рёбра.
10. Каждое пользовательское обещание, предназначенное для релиза, обязано иметь хотя бы один проходимый путь к реализации и один путь к проверке либо явный waiver с остаточным риском.

## Маршруты прослеживаемости

Путь вперёд по умолчанию:

`пользовательское обещание → доменное понятие → спецификация → контракт → тип/архитектура → реализация → тест/свидетельство → релиз`

Выборочный формальный путь может ответвляться от контракта или утверждения:

`контракт/утверждение → формальная модель → доказательство`

Опыт проекта возвращается через управляемый контур обратной связи:

`наблюдение → урок → RFC → проверка на эталонном проекте → изменение канона`

Обратная связь разрешена; скрытая мутация запрещена.
